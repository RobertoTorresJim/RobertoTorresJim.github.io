Los principios SOLID de programación orientada a objetos

"Para crear código compprensible, legible y comprobable en el que multiples desarrolladores puedan trabajar en colaboración"

Publicado por Roberto Torres J. en Septiebre 10, 2025

Los principios SOLID tiene cinco principios de diseño de clases orientadas a objetos son un conjunto de reglas y mejores prácticas a seguir y diseñar una estructura de clase.

Estos cinco principios nos ayudan a comprender la necesidad de ciertos patrones de diseño y arquitectura de software en general.

Antecedentes

Los principios Solid fueron introducidos por primera vez por el científico informático Robert J. Martin en uno de sus artículos de 2000. Sin embargo el acrónimo SOLID fue introducido más tarde por Michael Feathers.

Estos principios tienen como objetivo crear una codificación limpia por lo cual están estrechamente relacionados con la arquitectura orientada a objetos y patrones de diseño.

Por sus siglas en inglés estos principios son:

  • Principio de responsabilidad única (Single Responsability Principle)
  • Principio Abierto-Cerrado (Open-Closed Principle)
  • Principio de sustitución de Liskov (Liskov Substition Principle)
  • Principio de segregación de interfaz (Interface Segregation Principle)
  • Principio de inversión de dependencia (Dependency Inversion Principle)

Principio de responsabilidad unica

Este princpio nos dice que una clase debe hacer una cosa y por lo tanto debe tener una sola razon para cambiar.

Esto es que una clase e sun contenedor de datos, como una clase Libro, o una clase cliente, y tiene algunos campos relacionados con esta entidad, esta deberia cambiar solo cuando cambiamos el modelo de datos.

Para verlo de manera mas practica, considere el siguiente ejemplo:

class Coche{ String marca; Coche(String marca){this.marca = marca; } String getMarca(){return marca; } void guardaCocheDB(Coche coche){ ... } }

Analiza por un minuto y veamos por que este código viola el princpio de responsabilidad única.

Si bien es correcto que la clase coche contenga variables como la marca, el que esta misma clase pueda realizar operaciones de BBDD como guardar un coche está mal ya que se le está dando una nueva responsabilidad a la clase.

Suponiendo que se tuvieran que modificar los metodos para realizar operaciones en la BBDD. En este caso, además de estos cambios, es probale que también se tengan que realizar cambios a los nombres, tipo de propiedades, métodos, etc, lo cual resulta poco eficiente si solo estamos modificando cosas que tengan que ver con la BBDD.

Para tener la misma funcionalidad pero manteniendo el principio de responsabilidad única, lo ideal sería separar esta responsabilidad de guardado en BBDD en otra clase de la siguiente manera:

class Coche{
  String marca;
  Coche(String marca){this.marca = marca; }
  String getMarca(){return marca; }
}
class CocheDB{
  void guadaCoche(Coche coche){ ... }
  void eliminaCoche(Coche coche){ ... }
}

Con este simple cambio ahora si se está cumpliendo el princpio de responsabilidad única, teniendo un programa mucho más cohesivo.
